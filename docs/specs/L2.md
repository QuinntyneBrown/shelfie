# L2 - Detailed Requirements

Acceptance tests must carry a header comment such as `// Traces to: L2-002, L2-003` naming every L2 they cover. Viewport tiers: XS <576px, SM >=576px, MD >=768px, LG >=992px, XL >=1200px.

## L2-002: Sign in with username and password
**Traces to:** L1-001

Every person, parent or reader, signs in with a username and password.

**Acceptance Criteria:**
1. Given a parent's correct username and password, when submitted, then the parent lands on Review.
2. Given a reader's correct username and password, when submitted, then the reader lands on her shelf.
3. Given a username that differs from the stored one only in letter case, when submitted with the correct password, then sign-in succeeds.
4. Given an empty username or password, when submitted, then field-level errors are shown and no request is sent.
5. Given wrong credentials, when submitted, then one generic "username or password is wrong" error is shown that does not reveal which was wrong, and the typed username is kept.
6. Given a submission in flight, when the button is pressed again, then no second request is sent and the button shows a busy state.
7. Given the server is unreachable, when sign-in is submitted, then an error state with a retry action is shown.

---

## L2-003: Session lifetime and sign-out
**Traces to:** L1-001

The sign-in form offers "Remember me". A remembered session lasts while the person is active; an unremembered session ends with the browser. Sessions expire and the person is told why.

**Acceptance Criteria:**
1. Given "Remember me" checked at sign-in, when the browser is closed and reopened within 30 days, then the person is still signed in.
2. Given "Remember me" checked, when 30 days pass with no activity, then the next action sends the person to sign-in showing the "expired" message.
3. Given "Remember me" unchecked, when the browser is closed and reopened, then the sign-in page is shown and no protected data is displayed.
4. Given a person signs out, when they press Back, then no protected data is displayed.
5. Given sign-out, when completed, then the server session is invalidated.

---

## L2-004: Forgot and reset parent password
**Traces to:** L1-001

A parent can request a reset link by e-mail and set a new password. Readers have no e-mail and cannot reset this way.

**Acceptance Criteria:**
1. Given any well-formed e-mail, when submitted on Forgot password, then the same success message is shown whether or not the account exists.
2. Given a valid single-use reset link, when a new password of at least 8 characters is submitted twice identically, then the password changes and the parent is signed in on this device.
3. Given a used or expired link, when opened, then an error state is shown with an option to request a new link.
4. Given mismatching or too-short passwords, when submitted, then inline errors are shown.
5. Given a reset completes, when finished, then all existing sessions of that parent are invalidated.

---

## L2-005: Route authorisation
**Traces to:** L1-002

**Acceptance Criteria:**
1. Given no session, when any protected page or API is requested, then the user is sent to sign-in and the API returns 401.
2. Given a reader session, when a parent area (Review, Books, Manage book or Settings) is opened by URL, then the "Grown-ups only" page is shown and the API returns 403.
3. Given an unknown URL, when opened, then the Not found page is shown with a link home.
4. Given an unexpected server failure, when a page loads, then the Something went wrong page is shown with a retry action and no stack trace.

## L2-011: Log a chapter
**Traces to:** L1-004

**Acceptance Criteria:**
1. Given the next chapter of a book, when the reader answers question 1 and presses "I'm done!", then the chapter is saved as waiting for review and a success state is shown.
2. Given question 1 is blank, when she submits, then an inline error is shown; given other answers are blank, then submission succeeds.
3. Given an answer over 2000 characters, when typed, then input is limited and a counter is shown.
4. Given a half-written log, when she leaves and returns on the same device, then her draft is restored.
5. Given a successful submission, when the success toast shows, then Undo within the toast's lifetime reverts the log; after it ends, answers are final and cannot be edited.
6. Given the last chapter is logged, when submitted, then the finished-book celebration (L2-019) is shown.
7. Given the same chapter already logged, when a second log is submitted, then it is rejected.
8. Given the read-date choice (Today, Yesterday, Another day), when she picks one, then that date is saved with the chapter; a date in the future is rejected.
9. Given a chapter other than the next unlogged one, when a log is submitted, then it is rejected.
10. Given the questions, when the page opens, then Olive greets her and only question 1 is shown, with "N more questions after this one".
11. Given the shown question has an answer, when she presses "Next", then a short reply from Olive and the next question appear; "Next" is disabled while the answer is empty.
12. Given a draft with later answers, when the page opens, then every question up to the last answered one is shown.

## L2-023: Toasts and banners
**Traces to:** L1-010

**Acceptance Criteria:**
1. Given a completed action, when it succeeds or fails, then a toast with the matching severity is shown, announced by a live region, and dismissed after 8 seconds unless it has an action; the Undo toast after logging a chapter is the exception and lasts 10 seconds.
2. Given several toasts, then they stack with the newest nearest the edge.
3. Given a persistent condition such as offline, then a banner remains until the condition clears or the user dismisses a dismissible one.
4. Given hover or keyboard focus on a toast, then its timer pauses.
5. Given a danger toast, then it stays until dismissed or the retried action succeeds.

## L2-026: Accessibility
**Traces to:** L1-011

**Acceptance Criteria:**
1. Given any page, when navigated by keyboard only, then every action is reachable in a logical order with a visible focus indicator.
2. Given a dialog opens, then focus moves into it and is trapped; on close focus returns to the trigger.
3. Given any text, then contrast is at least 4.5:1 (3:1 for large text) in both light and dark themes.
4. Given form errors, then they are associated with their field and announced to assistive technology.

## L2-027: Credential and session security
**Traces to:** L1-012

**Acceptance Criteria:**
1. Given stored credentials, then passwords are stored only as salted, slow hashes (argon2id or bcrypt).
2. Given the session cookie, then it is HttpOnly, Secure, SameSite=Lax or Strict, and the token is rotated on sign-in.
3. Given state-changing requests, then a request without a valid CSRF defence is rejected.
4. Given repeated failed sign-ins from one source, then more than 10 attempts in 10 minutes are answered with 429.
5. Given responses, then CSP, X-Content-Type-Options, frame-ancestors and HSTS headers are set.
6. Given invite and reset tokens, then only their hashes are stored.

---

## L2-028: Input validation and output encoding
**Traces to:** L1-012

4. Given errors, then responses never expose stack traces, SQL or internal paths.

## L2-037: PostgreSQL as the system of record
**Traces to:** L1-014

The API stores all household data in PostgreSQL 16 and nothing on the application host's disk. The connection string is `DATABASE_URL`.

**Acceptance Criteria:**
1. Given `DATABASE_URL`, when the API starts, then it serves every request from that PostgreSQL database through a pool of at most 10 connections.
2. Given `NODE_ENV=production`, when the API connects, then the connection uses TLS and the server certificate is verified; a plain connection is refused.
3. Given the database is unreachable when the API starts, then the process exits with a non-zero code and one error line, and never listens for requests.
4. Given the database becomes unreachable while the API runs, then `GET /api/health` answers 503 within 5 s and ordinary requests answer 500 with a request id.
5. Given a chapter is logged, when the API answers 201, then the chapter log and its answers are committed in one transaction and survive an API restart (as `L2-031`).

---

## L2-038: Schema migrations
**Traces to:** L1-014

Schema changes ship as numbered SQL files in `apps/api/migrations` and run when the API starts.

**Acceptance Criteria:**
1. Given an empty database, when the API starts, then every migration is applied in file-name order, each in its own transaction, and recorded by name and time in `schema_migration`.
2. Given a database that already carries every migration, when the API starts again, then no migration runs and the data is unchanged.
3. Given a migration that fails, then its statements are rolled back, nothing is recorded for it, and the API does not start; the error names the file.
4. Given two API processes starting at the same moment, when both migrate, then each migration is applied exactly once.
5. Given the SQLite database of the current release, when `npm run import-sqlite -w apps/api` runs against an empty PostgreSQL database, then every household, profile, session, password reset, invite, book, chapter log, answer, question, reward and sign-in attempt row is present with the same values.

---

## L2-039: Database backup and restore
**Traces to:** L1-014

**Acceptance Criteria:**
1. Given the production server, then the service keeps automated backups for 7 days and can restore to any minute within that window.
2. Given 08:15 UTC each day, then a logical dump of the whole database is written to the `backups` blob container, and dumps older than 30 days are deleted by the storage account's lifecycle rule.
3. Given a dump and an empty database, when the documented restore runs, then the API starts against it and serves the restored households.
4. Given the dump fails, then the failure is logged under `shelfie-backup` and earlier dumps are untouched.

---

## L2-040: Database protection
**Traces to:** L1-012

**Acceptance Criteria:**
1. Given the database server, then it accepts connections only from the application's virtual network and has no public endpoint.
2. Given data at rest, then storage and backups are encrypted with AES-256 by the service.
3. Given a connection, then the server requires TLS 1.2 or later and the API verifies the server certificate.
4. Given the API's database role, then it owns the application schema only and has neither superuser nor replication rights; the administrator credential is held by the operator alone.
5. Given the connection string, then it is kept only in `/etc/shelfie/env` on the application host (mode 0640) and never in the repository, continuous-integration output, log lines or error responses.
6. Given the API fails to connect, then the error written to the log names the failure but not the password.

---

## L2-041: Household erasure and data retention
**Traces to:** L1-012

A household owns everything created for it. Self-service deletion and export screens are deferred; until they exist the operator runs the documented erasure.

**Acceptance Criteria:**
1. Given a household, when its row is deleted, then every profile, device, session, password reset, book, chapter log, answer, question and reward of that household is deleted in the same transaction and no row referencing it remains.
2. Given another household, when a household is erased, then the other household's data is unchanged.
3. Given expired sessions, spent or expired password-reset tokens and sign-in attempts older than the rate-limit window, when the nightly maintenance runs, then they are deleted.
4. Given the runbook, then it documents the erasure statement the operator runs and the maintenance schedule.

A parent manages their photo from Settings → Your account; a reader from "My photo" in her account menu. Both use the "Your photo" dialog (`docs/mocks/dialogs/profile-photo/`). 4. Given a person with a photo, when they press Remove photo, then the photo is deleted without a confirmation and their initial shows again everywhere.

7. Given any session, then it can add, replace or remove only its own photo; a parent cannot change a reader's photo or another parent's, and no API accepts a profile id for these actions.
8. Given XS, MD and XL viewports, then the dialog has no horizontal scroll and is a bottom sheet under 640 px (L2-025); it is keyboard-operable with focus returning to its trigger (L2-026).

## L2-044: Photo validation and processing
**Traces to:** L1-015

**Acceptance Criteria:**
1. Given a file whose content is not a JPEG, PNG or WebP image, whatever its name or declared type, when uploaded, then it is refused with 400 `photo-type`, nothing is stored and the dialog shows "Shelfie can’t use that file. Pick a JPEG, PNG or WebP photo."
2. Given a file larger than 5 MB, when chosen, then the browser refuses it without sending and shows "That photo is too big. Pick one under 5 MB."; a request body over 5 MB that reaches the API is refused with 413 `photo-too-large`.
3. Given an image whose decoded size exceeds 40 megapixels, when uploaded, then it is refused with 400 `photo-type` without being fully decoded.
4. Given an accepted photo, then the server applies its orientation, centre-crops it to a square, resizes it to 256 × 256 pixels and stores only that re-encoded WebP; the uploaded bytes are never stored.
5. Given a photo is served, then the response carries an `ETag`, and a request with a matching `If-None-Match` is answered 304 without a body.

## L2-045: Photo security and privacy
**Traces to:** L1-015

Applies L2-005, L2-006, L2-027, L2-029 and L2-041 to photos.

**Acceptance Criteria:**
1. Given no session, when a photo, an upload or a removal is requested, then the API answers 401 (L2-005).
2. Given two households, when household A requests a photo of a person in household B, then the response is 404 and no image data is returned (L2-006).

## L2-048: Cover picture validation, processing and security
**Traces to:** L1-003

Applies the photo rules of L2-044 and L2-045, and L2-005, L2-006, L2-010, L2-027, L2-029 and L2-041, to cover pictures.

**Acceptance Criteria:**

8. Given a book is removed (L2-010) or its household is erased (L2-041), then its cover picture is deleted in the same statement and no picture row for it remains.
9. Given logs, then they never contain image bytes (L2-029).

## L2-049: Admin tokens
**Traces to:** L1-017

The operator creates, lists and revokes admin tokens with a script run on the server (`npm run admin-token -w apps/api`). A token carries a name, one or both scopes (`read`, `write`) and an expiry.

**Acceptance Criteria:**
1. Given `admin-token create --name <1-40 characters> --scopes read|read,write --days <1-90>`, when run, then a token starting `shfa_` followed by 43 base64url characters is printed once, and only its SHA-256 hash, name, scopes, creation time and expiry are stored.
2. Given `--days` is omitted, when a token is created, then it expires 30 days after creation.
3. Given a name outside 1-40 characters, scopes other than `read` or `read,write`, or `--days` outside 1-90, when run, then the script exits non-zero with a message naming the bad option and stores nothing.
4. Given `admin-token list`, when run, then each token's id, name, scopes, expiry, last use and revocation time are shown and no token value or hash is shown.
5. Given `admin-token revoke <id>`, when run, then the next admin call with that token is refused with 401 `token-revoked`.

## L2-050: Admin API authentication and least privilege
**Traces to:** L1-017

Every admin API call carries `Authorization: Bearer <token>`. Admin tokens and web sessions never grant each other's access.

**Acceptance Criteria:**
1. Given no `Authorization` header, or a value that matches no token, when any admin endpoint is called, then the response is 401 with type `token-missing` or `token-invalid` respectively.
2. Given an expired token, when an admin endpoint is called, then the response is 401 with type `token-expired` and the expiry time.
3. Given a revoked token, when an admin endpoint is called, then the response is 401 with type `token-revoked`.
4. Given a token with only the `read` scope, when a write endpoint is called, then the response is 403 with type `scope-missing` and nothing changes.
5. Given a parent's web session cookie and no token, when an admin endpoint is called, then the response is 401.
6. Given a valid admin token and no session cookie, when a web endpoint such as `GET /api/review` is called, then the response is 401.
7. Given a token that passes, when the call completes, then the token's last-use time is updated.

## Assumptions (L2-049 to L2-063)

Decisions taken for the admin CLI without further input. Each is final unless the operator changes it.

1. The operator is the only admin. Admin tokens are not tied to a household or a profile; they see and change every household, because the operator runs the whole service.
2. Scopes are `read` (every query) and `write` (every change); a token with `write` always also has `read`. There is no finer scope.
3. Tokens are created, listed and revoked only by the server-side script, run by the operator over the existing SSH access (docs/runbook.md). The CLI itself never touches the VM, SSH or the database.
4. Device-code login is not offered (ADR-0001). The CLI stores the pasted token in the OS credential store: Windows Credential Manager, macOS Keychain or the Linux Secret Service (`secret-tool`).
5. The admin API has no IP allow-list; access rests on the token, HTTPS and the rate limit (ADR-0005).
6. The rate limit is 60 calls per minute per source address, kept in memory; a restart resets it.
7. "Reset a password" means the operator sets a new password for a parent. Readers' credentials stay with the household's parents (L2-036), and reset e-mail is not used because the production e-mail provider is deferred.
8. "Correct a log entry" covers the read-on day only. Chapter numbers and answers are the reader's own work and are not edited by the operator.
9. "Delete a log entry" is limited to the newest logged chapter of a book, matching the web app's undo rule, so chapters never have gaps.
10. "Mark a book finished" sets the finished time even when chapters remain unlogged; it is the operator's override.
11. Review feedback (stickers and notes) stays in the web app. The CLI shows review status but does not send feedback.
12. Answer text is shown by `logs show` because reviewing answers is part of the operator's role; it is never written to a log or the audit trail (L2-029).
13. The audit trail is read on the server (docs/runbook.md); there is no CLI command for it.
14. Admin reads fall under the existing read performance budget (L2-030).
15. The CLI targets .NET 10 and is distributed as a NuGet package built from the repository; it is not published to nuget.org.

## L2-076: The catalogue cover becomes the book's picture
**Traces to:** L1-020

A catalogue match may name a cover. The API fetches it from the catalogue's cover host, puts it through the cover rules of L2-048 and serves the result; the browser treats it as the chosen picture of L2-046 and uploads it with the book.

**Acceptance Criteria:**
1. Given a match with a `coverId`, then its small cover in the list and the picked picture are both loaded from `GET /api/books/search/covers/:coverId` on the API, never from the catalogue host directly.
2. Given a cover request, then the API fetches only `https://covers.openlibrary.org/b/id/<id>-L.jpg` where `<id>` is 1 to 12 digits, with a 5 second timeout and a 5 MB limit, and any other id or host is refused with 400.
3. Given the fetched bytes, then they pass the checks of L2-048 (JPEG, PNG or WebP by content, at most 40 megapixels) and are re-encoded to a 320 × 480 WebP without metadata before they are served; bytes that fail are answered 404 `photo-type` and nothing is stored.
4. Given a cover that cannot be fetched, is too large or is not an image, then the search still lists the match, its row shows the colour-and-sticker placeholder, and picking it fills the author and chapters without a picture.
5. Given a match with a cover is picked, then the preview shows the picture, "Change picture" and "Remove picture" appear, and when the book is added the picture is uploaded with it exactly as a chosen file is (L2-046), so the book shows the picture on the shelf.
6. Given a served cover, then it is `image/webp` with `Cache-Control: private, max-age=3600`, `X-Content-Type-Options: nosniff` and `Content-Security-Policy: default-src 'none'; sandbox`.
7. Given no session, when a cover is requested, then the API answers 401.
