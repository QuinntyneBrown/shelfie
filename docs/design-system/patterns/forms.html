Pattern · Input

Forms

Every form in Shelfie is a single column of labelled fields grouped into cards, checked when it is sent, with one primary button at the end. Nia's forms read like a friendly conversation; Dad's are short and plain.

Overview

Shelfie has a handful of forms and each does one job: log a chapter, add a book, send feedback, give a reward, change a book's details, change settings, sign in. They share one shape so neither Nia nor Dad has to learn a second one.

  • Labels sit above fields, always visible, never inside the field as placeholder text. For Nia the label is often the question itself ("What happened in this chapter?").
  • Related fields share a card. A <fieldset class="card"> with a <legend> groups each step ("When did you read it?", "Tell Dad about it", "Make a cover").
  • Only optional fields are marked, with a quiet "(optional)" after the label. Everything else is required.
  • Validation waits for submit. Nobody sees red while they are still typing. After the first submit, each field re-checks as it is edited, so errors clear as soon as they are fixed.
  • One primary button, last. The way out (ghost "Not yet", "Cancel") sits before it in .form-actions.
  • Destructive actions confirm in a dialog that starts on the safe button.

Built from form field, text field, textarea, radio group, chip, swatch picker, sticker picker, switch, alert, button and dialog.

A password field has a trailing show/hide button inside its text field group. A yes/no setting such as "Keep me signed in" is a switch, not a checkbox.

Validation and the error summary

On submit, every problem is found at once. The summary appears above the first card, takes focus and links each problem to its field. Each invalid field gets aria-invalid="true" and its own message, which says how to fix it.

Submitting

The pressed button shows its busy ring (aria-busy="true" plus disabled) and keeps its width. Text fields turn readonly, so what Nia wrote stays readable; chips, swatches and radios turn disabled. The way-out link stays usable on page forms; in dialogs every footer button is disabled until the request ends.

Autosaved drafts

Log a chapter is the only form that autosaves. Answers are saved as a draft every few seconds while Nia types, so a closed tab, a flat battery or "Not yet" loses nothing; the draft is back when she opens the same chapter again. The draft is never shown to Dad and is not a logged chapter until she presses "I’m done!". There is no Save button and no saving indicator: the saving is invisible because it should never be something she thinks about.

Section forms that Dad edits (Manage book → Details) do not autosave. They save on "Save changes" and report in the card header with an inline status:

Destructive confirmation

A destructive action lives in a .danger-zone at the bottom of the page. Its button opens a confirmation dialog; the dialog, not the page, holds the button that actually deletes.

Remove this book

Deletes Nia’s 11 logged chapters and answers for it too.

Remove book

Remove “The Lion, the Witch and the Wardrobe”?

Nia’s 11 logged chapters and answers for this book will be deleted too, along with your feedback. This can’t be undone.

If she just finished it, give a reward instead of removing it; finished books live on her trophy shelf.

Responsive behaviour

  • Forms are one column at every width. Fields that hold short values (chapters, name) cap their width so the box matches the answer.
  • Add a book shows a live cover preview beside the form from 1024px (.span-8 form, .span-4 aside); below that the preview drops under the form. Use the span classes, not an inline media query (drift D5).
  • Review a chapter keeps the feedback form beside the answers from 1024px with .sticky-aside; on phones it follows the answers.
  • .form-actions wraps; the primary stays last, so on a narrow phone it lands on its own line at the right.
  • Dialog forms become bottom sheets under 640px; see dialogs and overlays.

Accessibility

Role and pattern

Native <form>, <fieldset>/<legend>, <label for>, <input> and <textarea>. Day chips are toggle buttons (aria-pressed) in a role="group"; cover colour and sticker are native radios in a role="radiogroup". The confirmation follows the WAI-ARIA APG Alert Dialog pattern.

Keyboard

KeyAction
Tab / Shift+TabMoves through fields in reading order, then the actions.
EnterIn a single-line field, submits the form. In a textarea, adds a new line.
SpaceToggles a chip or sticker choice.
Arrow keysMove between cover colours, stickers and radio options.
Enter on a summary linkMoves focus to the field with the problem.
EscIn a dialog form, cancels and returns focus to the button that opened it.

Focus

On a failed submit, focus moves to the summary (tabindex="-1"), which is read out because it is role="alert". Pages put the first field in focus only when the form is the whole page (add a book). A confirmation dialog starts on the safe button, never the danger button.

Labelling

Every control has a visible <label for>; date and colour inputs without visible text use aria-label or a visually hidden label. Help and error are tied to the control with aria-describedby, error first. Required fields carry the required attribute; optional ones say "(optional)" in the label, so the rule is visible and announced.

Motion

Border and ring colours change over --duration-fast. Both go away under prefers-reduced-motion; the message still appears.

Touch

Fields and buttons are at least 44px tall; chips 36px with 12px between them; colour swatches 44px. The primary submit is large (52px) on Nia's forms.

Content

  • Labels for Nia are questions she can answer: "How many chapters?", "When did you read it?". Labels for Dad are nouns: "Number of chapters", "E-mail address".
  • Help text is a hint, not a rule list: "Count them in the contents page. You can change this later."
  • Field errors say how to fix it, in the same voice as the form: "Write a sentence or two about what happened. There are no wrong answers!"; "Use at least 8 characters."
  • Summary titles count the work: "One more thing" or "One thing to fix" for one, "Fix 2 things" for more. Summary lines are short and name the field: "Question 1 needs an answer".
  • Submit buttons say what happens: "I’m done!", "Add to my shelf", "Send to Nia", "Save changes". Never "Submit" or "OK".
  • Confirmations ask a question that names the thing ("Remove “The Lion, the Witch and the Wardrobe”?"), state the loss with a count ("11 logged chapters and answers"), and label both buttons with outcomes: "Keep the book" / "Remove book and answers".
  • Failures reassure first: "Everything you typed is still here; try again."
